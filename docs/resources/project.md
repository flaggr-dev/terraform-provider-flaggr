# flaggr_project (Resource)

Manages a Flaggr project.

## Example Usage

```terraform
resource "flaggr_project" "platform" {
  name        = "Platform"
  slug        = "platform"
  description = "Main platform project"

  # Optional: defaults to your only organization. Fixed once the project exists.
  organization_id = flaggr_organization.acme.id
}
```

## Updates and the description

An update sends only the attributes that changed. Any change needs the **Admin** tier, and a new `slug` needs the project owner with a personal access token: Flaggr refuses a slug change from a project API token (`fgr_…`), whoever owns the project.

Removing `description` from the configuration clears it in Flaggr (the provider sends an empty description; the API keeps any field it isn't sent). That includes a description set outside Terraform, for example in the dashboard: if the configuration has no `description`, the next apply clears it. To keep it, set `description` in the configuration, or add `lifecycle { ignore_changes = [description] }`. Flaggr reads back a project without a description and one with an empty description the same way, so `description = ""` and no `description` both converge.

## Organizations

A project can't move to another organization, and a project in no organization can't be added to one: Flaggr has no API or dashboard action for either. Changing `organization_id` on an existing project fails at plan time with "A project can't move to another organization" (a value known only during the apply fails the apply instead, before the project changes). Set it back to the project's organization, or remove it, which keeps the current one; for a project in no organization, remove it. A state with no organization recorded, planned with `-refresh=false`, is checked against the project's own organization the same way.

To have the project in the other organization instead, re-create it: `terraform taint flaggr_project.<name>`, then apply. That deletes the project in Flaggr (which needs a token with **Allow owner actions**: see Authentication on the provider's page) and creates a new one there, with a new ID. `terraform apply -replace` doesn't get that far, and neither does `terraform destroy`: while `organization_id` names another organization, both stop at the same check. Set `organization_id` back, or remove it, before destroying the project.

## Schema

### Required

- `name` (String) Project name.
- `slug` (String) URL-friendly identifier.

### Optional

- `description` (String) Project description. Without it in the configuration, an apply clears the project's description, including one set outside Terraform.
- `organization_id` (String) Organization ID this project belongs to. If omitted, defaults to the user's sole organization. Set when the project is created: a project can't move to another organization, so changing it on an existing project is an error.

### Read-Only

- `created_at` (String) Creation timestamp.
- `id` (String) Project ID.
- `updated_at` (String) Last update timestamp.

## Import

Import is supported using the following syntax:

In Terraform v1.5.0 and later, the [`import` block](https://developer.hashicorp.com/terraform/language/import) can be used with the `id` attribute, for example:

```terraform
import {
  to = flaggr_project.platform
  id = "your-project-id"
}
```

The [`terraform import` command](https://developer.hashicorp.com/terraform/cli/commands/import) can be used, for example:

```shell
# Projects are imported by project ID.
terraform import flaggr_project.platform "your-project-id"
```
